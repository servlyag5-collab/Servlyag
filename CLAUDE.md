# Servly AG: project notes for Claude Code

## What this app is
Servly AG ("Servly" when spoken) is a marketplace where local merchants list services (photographers, hairdressers, tutors, bus services, anything) and customers find them. Launch market: Antigua and Barbuda; later the wider Caribbean. Runs on Android, iOS and web from one codebase.
Tagline: "Whatever you need, someone's ready."

## Stack
- Expo + React Native + TypeScript, expo-router (routes live in `src/app/`). Use relative imports (no `@/` alias).
- Supabase: auth (email/password), Postgres with Row Level Security, Storage bucket `service-photos`.
- Env vars (in `.env`, never committed): `EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_ANON_KEY`, `EXPO_PUBLIC_PAY_URL` (empty until a payment provider is chosen).
- Website domain (owned, GoDaddy): **servlyag.com**. Web version hosted on Netlify (site startling-crumble-f0ead8.netlify.app, deployed by dragging the `dist` folder built with `npm run build:web` (export + `scripts/fix-web-assets.js`, which moves every font/icon from deep `dist/assets/node_modules/...` folders into one flat `dist/assets/fonts/` because Netlify Drop skips node_modules folders and lost the icon font in the nested ones); `public/_redirects` sends every path to the app). Netlify visibility is **Private until just before store submission** (owner's decision), then switch to Public. Planned uses: Privacy/Terms pages for the stores, the web version of the app, the payment page (EXPO_PUBLIC_PAY_URL), password-reset redirect, support email.
- Bundle id / Android package: `com.servlyag.app` (matches servlyag.com; decided by the owner on 2026-10-27. Never change it after the first store upload).
- Test on Android with Expo Go (no custom native code yet).

## Business rules (do not change without asking)
Three subscription tiers, set only by the owner in Supabase (merchants can never choose or change their tier, page layout, priority or free booking):
| Tier (id) | Price | Listings | Priority in search | Booking app |
|---|---|---|---|---|
| Starter (`basic`) | 50 XCD/month | 1 | no | add-on |
| Growth (`plus`) | 100 XCD/month | 2 | yes (after Business) | add-on |
| Business (`premium`) | 170 XCD/month | 4 | top (first) | included |
- All tiers: public business profile, direct customer messaging (notes) and call.
- Booking add-on: 25 XCD/month, per merchant. Starter/Growth merchants tick a checkbox on the Plan screen (`profiles.booking_requested`); `activate_plan` then charges the add-on and switches on `booking_enabled` for all their listings. (`services.booking_requested` is no longer used.)
- Merchant view: only users with at least one listing can switch between Customer and Merchant view (menu and Account). Publishing a first listing switches them to Merchant view.
- Merchants edit a listing (business details, service fields, photos) in `src/app/edit/[id].tsx`, reached from Account or the listing page. Hiding/showing a listing is not offered (re-showing could get around the tier's listing limit).
- Page layout (basic/plus/premium) comes only from the merchant's tier; see `Listing` in `src/app/service/[id].tsx`. The three layouts are placeholders until the owner defines them.
- Moving to a smaller plan (v20, owner's rule: no swapping): `services.paused` (merchants have no grant on it) hides a listing from customers (RLS policies, `search_services`, business profile) and frees its slot (`enforce_service_limit` counts live = active and not paused). Plan screen: choosing a tier whose `max_services` is below the merchant's live listings opens `KeepListings`; `rpc('choose_listings_to_keep')` stores exactly min(limit, live) ids in `profiles.keep_listings`. `activate_plan`: same tier = +1 month; bigger tier = switch now; smaller tier while still paid = `next_tier`/`next_tier_at` (= current expiry)/`next_booking`, month added after; smaller with no paid time = switch now. Any non-downgrade payment cancels a waiting move. `apply_plan_change` sets the tier, booking_enabled = included or add-on paid, and pauses live listings over the limit (kept ones first, then oldest). pg_cron `servly-plan-changes` (hourly, :05) runs `apply_due_plan_changes()` + push. Merchants read their waiting move with `rpc('my_plan_change')`. Paused listings come back only via `rpc('restore_listing')` (Account "Bring back", asks to confirm): needs an active plan, no waiting move, and a free slot; nothing can re-pause a listing except a plan change.
- Listings are visible to customers only while the merchant's `plan_expires_at` is in the future. Plans are activated by `select public.activate_plan('MERCHANT-ID','plus');` (adds one month, logs a payment).
- Photos: photo 1 is the cover (logo or best photo) shown on search, business and Account cards (`src/components/Cover.tsx`); photos 2-5 show as "Our work" on the listing page. Edit listing can reorder with "Make cover". The listing page shows the cover at 16:10 (`aspectRatio={1.6}`, same shape as Home cards).
- Photo focus points (v18): `services.photo_focus` jsonb `{ [photo path]: { x, y } }` (0-1; missing = centre). On Offer/Edit, tapping a photo opens `PhotoFramer` (drag inside a 16:10 frame, Centre / Cancel / Use this); the whole photo is still uploaded. Every cropped photo (Cover, Our work, Offer/Edit thumbnails) uses expo-image `contentPosition` via `focusOf` + `position` in `src/lib/focus.ts`; `cleanFocus` drops removed photos on save. Customers tap the cover or an Our work photo to open `PhotoViewer` (whole photo, swipe/‹ ›/arrow keys, n of N, gold dots, × / Escape / back to close).
- Demo covers: `supabase/demo-covers-v4/` (16 designed covers: icon + halo + flag ribbon, no words; preview `docs/demo-covers-preview.jpg`), uploaded to Storage `service-photos/demo/` and attached by `supabase/demo-covers.sql`.
- Offer a service shows plans first when the merchant has no active or chosen plan (Plan → Checkout → "Continue: create your listing"), shows "n of m listings used", and blocks the form at the limit. The limit is the PAID tier (database trigger), so an unpaid Growth choice still allows 1 listing until payment.
- Choosing a plan goes straight to `checkout.tsx` (order summary + Pay). Pay opens `EXPO_PUBLIC_PAY_URL`; until a provider is set it shows "Online payment is not connected yet".
- The owner viewing their own listing in merchant view sees a preview: banner "This is how customers see your listing" + Edit listing; Call, Business profile and the note form are disabled.
- Every inner screen uses `TopBar` (`src/components/Menu.tsx`): ← Back left, small Servly logo centred (tap = Home via `router.dismissTo('/')`), ☰ right.
- Search order (Home): Business listings first, then Growth, then Starter; newest first within each tier. This comes from `tiers.priority_rank` (premium 2, plus 1, basic 0), copied to `services.priority`.
- Loading: page and section loaders use `PinLoader` (`src/components/PinLoader.tsx`: the blue S pin from logo.png turning like a coin, shadow narrowing; `size` prop, 60 on app start, 30 for sections); button spinners and the search-box spinner stay as small ActivityIndicators. Home hero: the sun's faded outer glow is `SunGlow` (`src/components/SunGlow.tsx`): grows 8% and settles, 2.6 s each way, 3 times after the page opens, then still. Both are still for reduce-motion users.
- Opening animation (`src/components/Splash.tsx`, wired in `_layout.tsx`): about 3s, once per launch. The pin drops and bounces, the name slides in, a flag ribbon sweeps, then it fades to the app; it waits for the login check. Reduce-motion users get a still logo.
- Home search updates as you type: `LIVE_WAIT` (300 ms) after the last change to the text, Parish or Village it calls `search_services`; under 2 letters it shows everything; only the newest request may show results (`latest` ref); a spinner shows in the search box while loading. The Search button still searches immediately and scrolls to the results. Live search uses `search_services` from v20 (v19 rules + paused): substring match in name/description, word starts in tags, typo tolerance. **v21 (`upgrade-v21-search-word-starts.sql`) is written but NOT run** (owner's choice, may run later): it would match only the START of words in name/description/tags (`search_words()`), so "ac" no longer finds "packing"/"practice".
- Tags are search-only: merchants set them on Offer/Edit, search matches the whole phrase and each word against tags, and tags are never shown to customers. Under the tags box, `TagRules` shows an ⓘ Tag rules button: tags only for services the listing offers, no unrelated words to appear in more searches, penalties (hidden, suspended or removed; repeated misuse can close the account), backed by "Misleading listings" in the Terms (What is not allowed). Max 10 tags per listing (`MAX_TAGS`, `parseTags`, `tagsProblem` in `src/lib/tags.ts`; checked in the app on save, with an "n of 10 tags" counter; enforced in the database by check constraint `services_max_10_tags`, v17).
- The login/sign-up screen uses TopBar (Back + logo). The "No services found" card has a red border and no button (Clear filter is next to Search).
- Messages: two-way chat. One `conversations` row per customer + listing (merchant_id set by trigger from the listing; you cannot message your own listing), many `messages`. Only the two participants can read or write (RLS). Read markers are set with `rpc('mark_conversation_read')`; a trigger keeps `last_message` / `last_message_at` and marks the sender as read. Live updates use Supabase Realtime on `messages` and `conversations`. Screens: `messages.tsx` (list for the current view), `chat/[id].tsx` (bubbles + reply), listing "Send note" starts or continues the chat (`src/lib/chat.ts`). The customer phone is optional (stored on the conversation; merchant sees Call/WhatsApp). `inbox.tsx` only redirects to Messages; the old `notes` table is no longer written.
- Phone privacy (one switch per business): `profiles.show_phone` (default on) and `profiles.public_phone` (generated: the number when on, null when off). Other people can read only `public_phone`; the real `phone` column is not readable by anon/authenticated, and its owner reads it with `rpc('my_phone')`. Customer screens (listing Call button, business profile) use `public_phone`. The "Show my phone number to customers" switch (`src/components/PhoneToggle.tsx`) is on Account (for users with listings), Offer a service and Edit listing; the phone is only required when it is on.
- Contact support (☰ menu, merchant view; `support.tsx`): tickets in `support_tickets` (topic billing/listing/account/other). Users can only create and read their own; the owner answers in Supabase Table Editor by filling `reply` and setting `status` to resolved (replied_at is set automatically), and the merchant sees it live.
- Receipts (Account, merchant view): one per row in `payments`. `src/lib/receipt.ts` builds a branded HTML receipt (number `SRV-<year>-<id>`); phones get a PDF via expo-print + expo-sharing, web opens Print / Save as PDF. Seller details are the `SELLER` constant there.
- Reviews (per LISTING since v12): `reviews` has `service_id`; 1-5 stars + optional comment, unique per (service_id, customer_id); `merchant_id` is set from the listing by trigger. Only customers with a conversation about that listing can insert; they can edit (rating, comment) but never add a second review of the same listing. `service_ratings` gives each listing's average + total (Home cards, listing page); `merchant_ratings` gives the whole business (business profile). The listing page shows that listing's newest review only, then "Read all N reviews", with Write/Edit; long reviews and replies show 4 lines + "Read more" (MoreText); the business profile shows all the business's reviews, each labelled "About: <listing>". `reviews/[merchantId].tsx` lists all (optional `?service=` for one listing); `review/[serviceId].tsx` writes/edits. Merchants tap "Ask for a review" in a chat; the customer's Leave a review button opens that chat's listing.
- Home (and search results) show two swipe rows (`ListingRow`, split by `splitRows` in `src/lib/rows.ts`): "Popular picks" = the listings of the highest-paying plan present in the results (Business; if none, Growth; if none, Starter); "More local services" = everything else, highest-paying first (database order, newest first within each). A row is never shown empty. Owner's rule: headings never name a tier, so nobody can tell what a business pays. (`ListingRow` also supports `layers` for cards stacked in columns; not used now.) Every card is the same height (the rating line is always reserved) so stacked cards line up. Cards have the cover, rating ("New" when none), a two-line title, business name and price. Web gets ‹ › buttons. Planned: one row per category once categories exist.
- Prices: `services.price_from` marks a starting price. `formatPrice` (`src/lib/price.ts`) shows "From EC$500", "EC$30" or "Ask for price" everywhere. Merchants set it with the From button inside the price box (`PriceInput`) on Offer and Edit.
- Booking app (v13): merchants with it (`merchant_has_booking`: Business tier with an active plan, a booking add-on paid in the last 32 days, or a listing with booking_enabled; the app asks `rpc('has_booking_app')`) tap "Book this customer" in a chat -> `book/[conversationId].tsx` (Servly calendar + 30-minute time slots 7 AM-8 PM, `components/DateTimePicker.tsx`) -> insert into `bookings` (parties set by trigger from the chat, status pending). A trigger posts a `messages.kind = 'booking'` card; customers `rpc('respond_booking')` (Confirm/Decline), merchants `rpc('cancel_booking')`; each posts a chat message. pg_cron job `servly-booking-reminders` (every 15 min, `send_booking_reminders()`) posts `booking_reminder` messages 5 and 3 days before at 9:00 AM and on the day at 7:00 AM (or 2 h before if earlier). All times are Antigua time (UTC-4, `src/lib/bookings.ts`). `bookings.tsx`: merchant Bookings / customer My bookings with Upcoming/Past tabs. booking/booking_reminder messages can only be created by the database (`servly.system` flag).
- Password reset: "Forgot password?" on `login.tsx` calls `resetPasswordForEmail` with a redirect to `/reset-password` (web: the site origin; phones: `Linking.createURL`). `reset-password.tsx` reads the link (tokens after `#`, or `?code=`), signs in, then `updateUser({ password })`. Redirect URLs must be listed in Supabase Auth > URL Configuration. The reset message is the same whether or not the email exists. Supabase's default SMTP only emails team members; real customers need custom SMTP.
- Launch readiness (v14): `admins` table + `is_admin()`; Admin dashboard `src/app/admin.tsx` (admin_* RPCs: find merchants, activate plan, booking on/off, reply ticket, resolve report, hide listing). `reports` (listing/review/user) via `ReportButton`; `blocks` (enforced in messages/conversations/bookings insert policies via `is_blocked_between`); `reviews.reply` via `rpc('reply_to_review')`; `delete_my_account()` (payments kept with merchant_id set null); `search_services()` RPC (pg_trgm, security invoker) used by Home with `.range()` paging (PAGE = 30); push: `push_tokens` + `save_push_token`/`remove_push_token`, `send_push()` via pg_net to Expo, trigger `messages_push`, daily `plan_expiry_reminders` (pg_cron 13:00 UTC). App: `src/lib/push.ts` (registers after login, taps open `data.url`), `src/lib/photos.ts` (expo-image-manipulator, 1600 px, 0.7), `PlanBanner`, `LegalPage`/`src/lib/legal.ts` (DRAFT text), business name links to the profile. Payment webhook: `supabase/functions/payment-webhook` (Deno; excluded from tsc). Tests: `__tests__/` with jest-expo (`npm test`); `npm run typecheck`. EAS: `eas.json` (preview APK, production).
- Opening hours (v15, per listing): `services.show_hours` (switch; hours stay saved when off) + `services.hours` jsonb `{mon..sun: {open, from, to}}` ("HH:MM" Antigua time; to <= from means past midnight). `src/lib/hours.ts` (DEFAULT_HOURS, normalizeHours, hoursProblem, openStatus), `HoursEditor` on Offer/Edit, `HoursCard` on the listing page. Home cards show a small gold "Open" tag bottom left (price line) only while open; nothing when closed. `useNow()` re-checks every minute so Home and the hours card change at opening/closing time. Demo data: `supabase/demo-opening-hours.sql` (6 demo businesses, today stretched to include the run time). Tests in `__tests__/hours.test.ts`, `HoursEditor.test.tsx`, `ListingRow.test.tsx`.
- Screen names (v16): `profiles.screen_name` (sign-up field "Screen name", editable on Account; max 40, repeats allowed) vs `display_name` (= business name, set on Offer/Edit; Account shows Business name only for users with listings). `conversations.customer_as_business` and `reviews.as_business` are set from the current view when the chat/review is created (a trigger forces false for users without listings) and never change. Show customer names with `customerName(profile, asBusiness)` from `src/lib/names.ts`; merchant names stay `display_name`. `push_new_message()` uses the same rule.
- Refund and Cancellation Policy (`src/app/refunds.tsx`, text `REFUNDS` in `src/lib/legal.ts`, DRAFT): no refund once a month has started; cancel through Contact support (no self-service cancel until the bank gateway is connected); billing mistakes refunded if reported within 30 days. Terms point to it; Checkout and the Plan screen link it. `LegalLinks` shows it always on the website (banks check the footer as a visitor) but in the phone apps only to merchants (`refund` prop: Account in merchant view); customers never pay Servly, so guests/customers in the apps see only Terms and Privacy.
- Customers send a **note** to a listing (phone/WhatsApp optional), which starts a two-way conversation. They do NOT book times yet.
- Photos: optional, max 5 per service, chosen when the service is published.
- City and Village on Offer/Edit and in the Home search (labelled Parish / Village there) are searchable pickers (`PlacePicker`): City lists the parishes (St. George, St. John, St. Mary, St. Paul, St. Peter, St. Philip, Barbuda), Village lists villages; both from `src/lib/places.ts` (edit there to add places). Merchants can also use a place that isn't listed. City is still required, Village optional. Still plain text in the database (no DB change).
- Village is an optional field on services and in search. City/Village/text search ignores empty fields (there is no price filter).

## Important cautions
- The code was written without being run. Expect small bugs; run `npx tsc --noEmit` and `npx expo-doctor` after changes.
- Never expose a Supabase service-role key in the app. Only the anon key goes in `.env`.
- Keep Row Level Security on every table; column-level grants stop merchants editing `tier_id`, `priority`, `booking_enabled`.
- App-store billing: Apple and Google generally require their own billing for paid features unlocked in-app. Charging merchants on the web is a common approach; check current rules before publishing.
- The owner is new to coding: explain what you are doing in plain English, make small steps, and ask before deleting files or changing the database design.
- `profiles` links to `tiers` twice (`tier_id` and `requested_tier`), so embed it as `tiers!tier_id(...)`, not `tiers(...)`, or Supabase returns "more than one relationship was found".
