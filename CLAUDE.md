# Servly AG: project notes for Claude Code

## What this app is
Servly AG ("Servly" when spoken) is a marketplace where local merchants list services (photographers, hairdressers, tutors, bus services, anything) and customers find them. Launch market: Antigua and Barbuda; later the wider Caribbean. Runs on Android, iOS and web from one codebase.
Tagline: "Whatever you need, someone's ready."

## Stack
- Expo + React Native + TypeScript, expo-router (routes live in `src/app/`). Use relative imports (no `@/` alias).
- Supabase: auth (email/password), Postgres with Row Level Security, Storage bucket `service-photos`.
- Env vars (in `.env`, never committed): `EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_ANON_KEY`, `EXPO_PUBLIC_PAY_URL` (empty until a payment provider is chosen).
- Website domain (owned, GoDaddy): **servlyag.com**. Web version hosted on Netlify (site startling-crumble-f0ead8.netlify.app, deployed by dragging the `dist` folder built with `npm run build:web` (export + `scripts/fix-web-assets.js`, which moves every font/icon from deep `dist/assets/node_modules/...` folders into one flat `dist/assets/fonts/` because Netlify Drop skips node_modules folders and lost the icon font in the nested ones); `public/_redirects` sends every path to the app). Netlify visibility is **Private until just before store submission** (owner's decision), then switch to Public. Planned uses: Privacy/Terms pages for the stores, the web version of the app, the payment page (EXPO_PUBLIC_PAY_URL), password-reset redirect, support email.
- Bundle id / Android package: `com.servlyag.app` (matches servlyag.com; decided by the owner on 2026-10-27. Never change it after the first store upload).
- Test on Android with Expo Go (no custom native code yet).

## Business rules (do not change without asking)
Three subscription tiers, set only by the owner in Supabase (merchants can never choose or change their tier, page layout, priority or free booking):
| Tier (id) | Price | Listings | Priority in search | Booking app |
|---|---|---|---|---|
| Starter (`basic`) | 50 XCD/month | 1 | no | add-on |
| Growth (`plus`) | 100 XCD/month | 2 | yes (after Business) | add-on |
| Business (`premium`) | 170 XCD/month | 4 | top (first) | included |
- All tiers: public business profile, direct customer messaging (notes) and call.
- Booking add-on: shown to merchants as an UPGRADE that names the benefit, never "add-on" (owner's choice): Plan checkbox "Upgrade to bookings: let customers book you" + "Fill your calendar without back-and-forth messages · +25 XCD / month" + "Or get bookings included with Business"; Checkout line "Bookings upgrade"; receipts "Bookings upgrade, 1 month"; chats show merchants without it a dashed "Upgrade to book this customer" chip (opens Plan). 25 XCD/month, per merchant. Starter/Growth merchants tick a checkbox on the Plan screen (`profiles.booking_requested`); `activate_plan` then charges the add-on and switches on `booking_enabled` for all their listings. (`services.booking_requested` is no longer used.)
- Merchant view: only users with at least one listing can switch between Customer and Merchant view (menu and Account). Publishing a first listing switches them to Merchant view.
- Merchants edit a listing (business details, service fields, photos) in `src/app/edit/[id].tsx`, reached from Account or the listing page. Hiding/showing a listing is not offered (re-showing could get around the tier's listing limit).
- Page layout (basic/plus/premium) comes only from the merchant's tier; see `Listing` in `src/app/service/[id].tsx`. The three layouts are placeholders until the owner defines them.
- Moving to a smaller plan (v20, owner's rule: no swapping): `services.paused` (merchants have no grant on it) hides a listing from customers (RLS policies, `search_services`, business profile) and frees its slot (`enforce_service_limit` counts live = active and not paused). Plan screen: choosing a tier whose `max_services` is below the merchant's live listings opens `KeepListings`; `rpc('choose_listings_to_keep')` stores exactly min(limit, live) ids in `profiles.keep_listings`. `activate_plan`: same tier = +1 month; bigger tier = switch now; smaller tier while still paid = `next_tier`/`next_tier_at` (= current expiry)/`next_booking`, month added after; smaller with no paid time = switch now. Any non-downgrade payment cancels a waiting move. `apply_plan_change` sets the tier, booking_enabled = included or add-on paid, and pauses live listings over the limit (kept ones first, then oldest). pg_cron `servly-plan-changes` (hourly, :05) runs `apply_due_plan_changes()` + push. Merchants read their waiting move with `rpc('my_plan_change')`. Paused listings come back only via `rpc('restore_listing')` (Account "Bring back", asks to confirm): needs an active plan, no waiting move, and a free slot; nothing can re-pause a listing except a plan change.
- Free trials (v22, Founding Merchants): `free_trials` table (one row per merchant, unique; RLS: read own; written only by `start_free_trial`, server key, or `admin_start_free_trial` from Admin > Start free trial, days default 90, 1-365). Only for merchants with no active plan and no earlier trial. It runs `apply_plan_change` and sets `plan_expires_at` = trial end, with NO `payments` row (no receipt). Free time counts like paid time (moves down wait; a payment adds its month after the trial). Booking during a Starter/Growth trial only if the admin ticks it (`free_trials.booking`, checked by `merchant_has_booking`). Account/Plan show `planStatus` ("free trial until") via `myTrialEnd` in `src/lib/trial.ts`; PlanBanner and the 3-day push say "free trial". No price lock or founder badge (not built).
- Promo codes (v23): `promo_codes` (code in capitals, percent_off, months, max_uses, active; not readable by users) and `promo_redemptions` (one per merchant, unique, ever; `hold_until` = apply + 7 days; `months_used`). Seeded LAUNCH50 and LAUNCH50B (50% off, 2 months, 25 places each), both OFF until the owner switches them on (Admin > Promos, `admin_promo_codes` / `admin_set_promo_active`). A place counts once paid or while held (`promo_places_taken`). Checkout: `rpc('apply_promo_code')` (refuses merchants with a free trial, a used code, or a full/off code; replaces an unpaid hold), `my_promo`, `remove_my_promo`; sums in `src/lib/promo.ts`. `next_promo_discount(user, tier)` = plan price x percent while months remain (held or already paid); `activate_plan` subtracts it (plan only, never the add-on), bumps `months_used`, and writes `payments.discount` + `payments.promo_code` (shown on receipts). The webhook expects the discounted amount. `start_free_trial` refuses merchants who paid with a code and frees an unpaid hold. `admin_find_merchants` returns a `promo` line for the merchant card.
- Admin controls (v26, Admin > Merchants card): `admin_change_plan(user, tier, booking)` = `apply_plan_change` with no payment/receipt (end date kept, waiting move and requested_tier cleared, returns listings paused); `admin_extend_plan(user, days 1-365)` adds days from now or the current end; `admin_merchant_listings(user)` + `admin_set_listing_on(service, on)` (on = active true and paused false, may exceed the plan limit on purpose). All check `is_admin()`. v27 adds the RLS policy "admins read all services" (`is_admin()`), so admins can open any listing; the listing page (`src/app/service/[id].tsx`, `maybeSingle`) shows the owner/admin a red banner saying why customers can't see it (Turned off / Paused / Plan ended), and anyone else a plain "This listing isn't available right now" instead of a database error.
- Free bookings (v28): `profiles.free_booking_until` (owner-only; no merchant grant). `merchant_has_booking` = Business plan with time left OR bookings upgrade paid in the last 32 days OR free trial with booking OR `free_booking_until > now()`; `services.booking_enabled` NO LONGER counts (the old Admin "Booking on/off", `admin_set_booking`, stayed on forever and is no longer in the app). Admin card: days + "Bookings on (no charge)" (`admin_free_booking(user, days)`, adds from now or the current end), "Off" (`admin_stop_free_booking`), and a line from `booking_source()` (business / paid / trial / free). `admin_find_merchants` returns `booking_source` and `free_booking_until`.
- Call taps (v29, OWNER-ONLY for now; owner's choice 2026-11-03: merchants get the numbers in a later normal update, no DB change needed then): `call_taps` (merchant_id, service_id or null for the business profile, source listing/profile, created_at; RLS on, no policies, no grants: no names or numbers stored). `callBusiness()` in `src/lib/calls.ts` (listing page + business profile Call buttons) calls `rpc('record_call_tap')` (anon too; only businesses with a public phone; repeat tap on the same listing/profile within 1 minute ignored; a business calling itself isn't counted) then opens `tel:`. Live search uses `search_services` from **v31** (`upgrade-v31-fair-turns.sql`, owner's rule 2026-11-06: Business plan first, but everyone gets seen): same matching as v30, but ORDER = business-name match first, then `priority` desc (Business, Growth, Starter), then `search_turn(id)` (md5 of id + the current half hour; `search_turn_minutes()` = 30), then id, so every listing in a plan takes turns at the front and paging is stable within a half hour. `search_suggestions` (v31): businesses whose name OR a live listing's title/tags match; order = name typed (`named`) first, then 2 spots for the highest plan present, then 1 spot shared in turn by all other plans. Never re-run v30 (or older search files) after v31. Before v31 it was **v30** (`upgrade-v30-ranked-search.sql`, 2026-11-03; it REPLACES v19/v21/v24/v25 search and re-creates their helpers: never re-run any of those after v30. On 2026-11-03 the live DB was found running v21 again because it had been re-pasted after v25). v30 = best match first: score = 10 per typed word in the business name + 10 in the title + 5 in tags + 1 in the description, +40/+30 when the whole typed phrase is in the title, +100 for a business-name match; plan priority then newest only break ties. A business-name match (typed phrase at a word start in `display_name` covering half the name, or 2+ words and 6+ letters, or similarity >= 0.6) shows ONLY that business. Description-only matches are dropped when some listing matches in name/title/tags. `search_suggestions(q)` (anon too, security invoker) returns up to 3 businesses (`service_id` when they have one listing, else open the profile) and 3 service titles; `SearchSuggestions` (`src/components/SearchSuggestions.tsx`) shows them under the Home search box while it is focused (250 ms after typing; a service suggestion searches for it). `splitRows` still splits rows by plan, keeping relevance order within each row. Before v30 it was v25 (, owner's rule 2026-11-02: "clean" must find cleaning in every field, without v24's "ac finds packages"): title, description, tags AND business name (`profiles.display_name`) in one text (`search_norm()`); each typed word is checked by `search_word_found()`: its root (`search_stem()` from v24: cleaner/cleaning -> clean, plumber -> plumb, roots keep 4+ letters) matches anywhere when 4+ letters, only at the start of a word when 2-3 letters ("ac", "dj"); spelling mistakes forgiven for 4+ letter words (similarity > 0.45). Listings must have EVERY word; if none has them all, listings with ANY word show. v21 and v24 were run on 2026-11-02 and are REPLACED by v25; never re-run either after v25.

## Important cautions
- The code was written without being run. Expect small bugs; run `npx tsc --noEmit` and `npx expo-doctor` after changes.
- Never expose a Supabase service-role key in the app. Only the anon key goes in `.env`.
- Keep Row Level Security on every table; column-level grants stop merchants editing `tier_id`, `priority`, `booking_enabled`.
- App-store billing: Apple and Google generally require their own billing for paid features unlocked in-app. Charging merchants on the web is a common approach; check current rules before publishing.
- The owner is new to coding: explain what you are doing in plain English, make small steps, and ask before deleting files or changing the database design.
- `profiles` links to `tiers` twice (`tier_id` and `requested_tier`), so embed it as `tiers!tier_id(...)`, not `tiers(...)`, or Supabase returns "more than one relationship was found".
